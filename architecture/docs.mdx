# Livora

Livora is a personal digital library and reading-companion app: a catalog of
books, a desk for active reading, a commonplace book for notes and quotes,
and a retrieval-minded "librarian" layer on top of it all. It is built for
one reader, with an editorial, archival visual language — closer to a
library's reading room than a typical SaaS dashboard.

This document describes what the app does, how it's put together, and why
it's built the way it is. It intentionally omits anything specific to the
private source repository (paths, internal tickets, deployment secrets).

## Core Features

### The Catalog
The full book catalog: search, filter by reading status and collection,
sort, and drill into a book's record page. Each book record carries rich
bibliographic metadata (edition, publisher, original publication year,
ISBN, shelf), a reading-status lifecycle, and a detailed, multi-criterion
rating model (premise & execution, writing & craft, depth of ideas,
internal structure, impact, staying power, rereadability) in addition to
an overall score — closer to a critic's rubric than a single star rating.

Books can be marked **owned** or **wanted** (not yet acquired). Wanted
books participate fully in reading-goal collections (see below) but are
excluded from every "how big is my library" metric elsewhere in the app.

### The Reading Desk
A desk view of every book currently being read: progress bars, session
estimates, reading-pace insight ("at this rate, you'll finish in N days"),
and a reading-goal line (pages/minutes/chapters/verses per day or week) set
per reading. Logging a session updates progress and, when a goal is
active, lets the reader mark whether that day's goal was hit — a UI-only
checkbox, not a separate persisted record, kept deliberately lightweight.

Reading sessions themselves are a full log: date, page reached, minutes
spent, with edit/delete support and validation against the book's own
reading history (no illegal page regressions, no sessions before the
reading started).

### Commonplace
A commonplace-book-style feed of personal annotations, typed by kind
(quote, idea, reflection, reading note, reference, concept), each
optionally linked to a source book and tagged with concepts. Concepts form
a lightweight knowledge graph across entries — the foundation for later
retrieval ("have I seen this idea before?").

### Shelves
A visual, physical-shelf-inspired browsing mode: books rendered as spine
blocks (height/width/tone varied for a believable stacks look), grouped by
shelf and sortable by color, author, or title. A deliberate contrast to the
Catalog's table view — the same data, read spatially instead of textually.

### Collections
Collections are curated, meaningful groupings — not just tags. Each has a
title, optional description, an accent color, and derived stats (volume
count, read count, a palette of spine tones for a visual signature).

A collection can be flagged as a **reading goal**: an optional target date,
and progress tracked as "N of M read." Reading-goal collections are the
one place in the app where owned and wanted books are treated identically
— a goal like "read 12 philosophy books this year" should be able to
include books not yet bought.

### Analytics (Weekly Review)
Weekly reading-rhythm review: pages read per day, books finished/added/in
progress that week, and a "share as image" export for each — generated by
rendering an off-screen, fixed-size (1080×1920) component and capturing it
to PNG, sized for a phone screen rather than a desktop viewport.

### The Librarian
A retrieval-first assistant layer, intentionally scoped to answer only
from the reader's own stored data — never inventing a prior reading, quote,
or note. Query classes it's built around: "have I seen this idea before?",
"connect this note to other books," "what should I revisit this month?",
"summarize recurring themes in my recent notes." Answers are expected to
carry citations back to the entities (books, entries, concepts) they're
grounded in.

## Folder Structure

```
app/
├── gabinete/         # Home dashboard — greeting, active read, recent activity
├── biblioteca/       # The Catalog — search, filters, book record pages
│   └── [slug]/       # Single book record: metadata, ratings, actions
├── mesa/             # The Reading Desk — active reads, session logging
├── commonplace/       # Notes/quotes feed, entry create/edit dialogs
├── estantes/         # Shelves — spine-block visual browsing
├── colecoes/         # Collections — index + detail pages
│   └── [slug]/       # Single collection: books, stats, goal progress
├── afericoes/        # Analytics — weekly review + image export cards
├── sign-in/          # Auth (Clerk)
└── sign-up/          # Auth (Clerk)

components/
├── atoms/            # Smallest building blocks (Button, Typography, ...)
├── molecules/        # Composed UI (dialogs, cards, menus)
├── organisms/        # Larger composed sections (nav, panels)
└── templates/        # Page-level layout shells (AppShell, ...)

data/
├── queries/          # Server-only Prisma reads, one module per domain area
├── actions/          # Server actions (mutations), Zod-validated
├── schemas/          # Zod schemas — the mutation input contract
├── mappers.ts         # Prisma row → view-model translation
└── types.ts          # View-model types — the UI's actual data contract

lib/                  # Cross-cutting helpers (dates, formatting, ...)

prisma/
├── schema.prisma     # Domain model (see Architecture below)
├── migrations/        # One directory per schema change, applied in order
└── seed.ts            # Deterministic starter data
```

The pattern repeats across every feature area: a page under `app/` loads
data via `data/queries/*`, renders it through components, and any user
action flows through `data/actions/*` guarded by a schema in
`data/schemas/*`. A new feature rarely needs a new architectural layer —
usually just one more module in each of these four places.

## Architecture

**Stack:** Next.js (App Router), TypeScript, Tailwind CSS v4, Prisma ORM
over Postgres (Neon), Zod for input validation, Clerk for authentication.

**Pages load data on the server.** Every primary route composes its data
from `data/queries/*` — server-only Prisma query functions — and passes
plain, typed view models down as props. Client components stay focused on
interaction (dialogs, forms, filters); they never query the database
directly.

**Mutations go through server actions**, each backed by a Zod schema that
validates the input shape *before* it reaches Prisma. A mutation's result
is a plain discriminated union — `{ ok: true }` or `{ ok: false,
fieldErrors, message? }` — so client forms can render field-level errors
without a separate error-handling path per action.

**Database rows never leak into the UI layer directly.** A dedicated
mapper layer (`data/mappers.ts`) translates Prisma row shapes into the
app's own view-model types (`data/types.ts`). This is deliberate decoupling:
the UI's contract is the view model, not the schema, so a column rename or
a new join doesn't ripple into every component that happens to render that
data.

## Key Design Decisions

**Soft ownership, not a separate "wishlist" entity.**
Rather than modeling "books I want to read but don't own" as a different
kind of record, a `Book` simply carries an `owned` boolean. This keeps one
book one row, one history, one slug — a wanted book that gets bought
becomes "owned" in place, without migrating it between tables or losing
any commonplace entries or collection memberships it had while wanted. The
cost is that every query representing "the library" (catalog search,
shelves, analytics, current reads) has to explicitly filter to owned
books — a convention enforced by habit and code review, not a database
constraint, since the one deliberate exception (reading-goal collections)
needs to see both.

**Reading goals live on the `Reading`, not the `Book`.**
A pace goal (pages/minutes/chapters/verses per day/week) is attached to
the specific reading attempt, not the book itself. A book read twice can
have different goals each time; archiving or restarting a reading doesn't
carry a stale goal forward by accident.

**Collections as a first-class intellectual unit, with one dual-purpose flag.**
Rather than building a separate "Reading Goals" feature with its own data
model, a reading goal is a `Collection` with `isReadingGoal: true` and an
optional `targetDate`. This means every piece of collection machinery —
assignment, stats, detail pages, filters — is reused for free, and a
collection can *become* a reading goal (or stop being one) without a data
migration.

**Soft-archive over hard delete.**
Books, collections, and commonplace entries all carry an `isArchived`
flag rather than being deleted outright. Reading history has retrospective
value — an abandoned book or a renamed collection is still part of the
reader's actual history, and the app treats "I don't want to see this
anymore" as distinct from "this never happened."

**Mocks-as-seed, not mocks-as-source.**
The original phase-1 build used fully static, typed mock data to get the
visual language and page structure right before any database existed.
Phase 2 kept those same mock shapes as the seed script's source data and as
the view-model contract (`data/types.ts`) — so the migration to Postgres
changed *where* the data came from, never *what shape* it arrived in, and
no page needed a structural rewrite to go live.

**Retrieval over generation, for the librarian.**
The AI layer is explicitly retrieval-first: it answers from the reader's
own stored books/entries/concepts and cites what it used, rather than
free-generating observations about the reader's history. The model
provider (OpenAI or Anthropic) is swappable behind a shared interface —
provider selection is a configuration concern, not something retrieval,
ranking, or citation formatting should ever need to know about.

**Desktop-first, not desktop-only.**
The editorial visual language — long-form reading widths, generous
whitespace, a fixed sidebar — is designed for desktop first, since that's
where most reading and cataloging happens. Mobile gets the same layout
primitives reflowed, not a separate product language; exported images
(analytics, quotes, evaluations) are sized and typographically tuned for
a phone screen specifically, since that's where they're actually viewed
after being shared.
